# StockTrade Architecture & Business Decisions Record (DECISIONS.md)

This document formalizes all architectural, financial, database, and algorithmic decisions for the **StockTrade** project, adhering strictly to the specification.

---

## 1. Monetary and Precision Rules
- **Database Types**:
  - Currency balances, amounts, ledger entries, fees, commissions: `DECIMAL(15,2)`.
  - Share prices: `DECIMAL(12,4)`.
  - Share quantities: `INT UNSIGNED`.
- **Backend Rules**:
  - Python's standard `decimal.Decimal` is used exclusively with `ROUND_HALF_UP` rounding.
  - Floating point types (`float`) are strictly forbidden for all financial calculations, balances, fees, and metrics.

---

## 2. Opening Balance & Signup Grants
- **Investor Initial Balance**:
  - `Accounts.virtual_balance` starts with the configurable virtual signup grant (default: `₹1,00,000.00`).
  - An immutable opening ledger row is created in `Account_Ledger` with:
    - `entry_type = 'OPENING_GRANT'`
    - `amount = +100000.00`
    - `balance_after = 100000.00`
    - `reference_type = 'SYSTEM'`

---

## 3. Order Execution & Idempotency
- **Market Orders**:
  - Orders execute immediately against the server-side authoritative price fetched inside an atomic row-locked transaction (`SELECT ... FOR UPDATE`).
  - Browser/client specifies only `stock_id`, `side` (`BUY` or `SELL`), `quantity`, and an `idempotency_key` (UUID v4 generated by client).
  - Any estimated price in the UI is purely illustrative.
  - If the live execution price diverges from the user's estimated quote by more than a configurable threshold (`PRICE_MOVED_TOLERANCE_PCT = 1.0%`), execution can abort with HTTP `409 Conflict (PRICE_MOVED)`.
- **Workflow State Machine**:
  - Order begins as `PENDING`.
  - If validations pass and transaction succeeds: order transitions to `EXECUTED` atomically with holdings, ledger, transactions, and commissions.
  - If validation fails (insufficient funds, insufficient holdings, inactive stock): transitions to `REJECTED` with an explicit `reject_reason`.
  - On system error / deadlock / lock timeout: rolled back and recorded as `FAILED`.
- **Idempotency**:
  - Unique composite index `(user_id, idempotency_key)` on `Orders`.
  - Retrying an identical idempotency key returns the previously executed order's result without re-executing.

---

## 4. Charges, Fees & Platform Commissions
- **Investor Brokerage (Investor-Paid)**:
  - Computed per trade: `brokerage = max(min_fee, trade_value × rate)`
  - Configured in `Commission_Rules` under rule type `INVESTOR_BROKERAGE`:
    - Default rate: `0.10%` (`0.0010`)
    - Default minimum fee: `₹1.00`
  - Charged on both `BUY` and `SELL`.
  - Recorded as a dedicated ledger entry: `entry_type = 'FEE'`, signed as a negative amount `-brokerage`.
- **Broker Commission (Platform-Funded)**:
  - Stored under rule type `BROKER_COMMISSION`: default `40%` (`0.40`) of the brokerage collected from trades executed by investors assigned to that broker.
  - Platform-funded and reporting-only: it does **not** cost the investor extra and is **never** deducted from the investor's balance.
  - Exactly one commission row per executed transaction in `Commissions` (unique constraint on `transaction_id`).
  - Investors with no active broker assignment generate `0` commissions.
  - Rules apply to future trades based on `effective_from`; the exact rate used is frozen in the `Commissions` record (`rate_applied`, `commission_amount`).

## 5. Cost Basis and P&L Calculations
- **Weighted Average Cost**:
  - On `BUY`:
    $$\text{new\_avg\_cost} = \frac{(\text{old\_qty} \times \text{old\_avg}) + (\text{qty} \times \text{execution\_price})}{\text{old\_qty} + \text{qty}}$$
    Brokerage is accounted for separately in ledger fees and is not blended into the share cost basis.
  - On `SELL`:
    $$\text{realised\_pnl} = (\text{sell\_price} - \text{avg\_cost}) \times \text{sell\_qty} - \text{sell\_brokerage}$$
    Average cost does not change on partial sale.
  - When holding drops to 0 quantity: the row is kept with `quantity = 0` or updated cleanly, and transaction audit trail remains intact.

---

## 6. Portfolio Metric Definitions (`portfolio_service`)
1. **Available Cash**: $\sum(\text{ledger signed amounts})$ (`OPENING_GRANT` + `DEPOSIT` + `SELL` proceeds - `BUY` costs - `FEE`s).
2. **Holdings Market Value**: $\sum(\text{holding.quantity} \times \text{current\_price})$.
3. **Total Portfolio Value**: $\text{Available Cash} + \text{Holdings Market Value}$.
4. **Unrealised P&L**: $\sum(\text{holding.quantity} \times (\text{current\_price} - \text{avg\_cost}))$.
5. **Realised P&L**: $\sum(\text{sell transaction realized P\&L net of sell-side brokerage})$.
6. **Return %**: $\frac{\text{Total P\&L}}{\text{Cost Basis}} \times 100$, or `null` (`"—"`) when cost basis is zero.
7. **Today's P&L (approximate)**: $\sum(\text{holding.quantity} \times (\text{current\_price} - \text{previous\_close}))$.

---

## 7. Data Immutability & Soft Deletion
- Financial records (`Account_Ledger`, `Transactions`, `Orders`, `Commissions`, `Audit_Logs`) are strictly append-only. Triggers block any `UPDATE` or `DELETE` on `Account_Ledger`.
- Users, Accounts, and Stocks are soft-deactivated via `status = 'INACTIVE'`.
- Hard deletion of a stock is guarded and allowed if and only if zero orders, zero holdings, zero alerts, and no prices exist beyond initial seed.

---

## 8. Concurrency & Deadlock Prevention
- All trade executions acquire row locks using a strict global lock hierarchy:
  1. `Accounts` row (`SELECT ... FOR UPDATE WHERE id = :account_id`)
  2. `Holdings` row (`SELECT ... FOR UPDATE WHERE user_id = :user_id AND stock_id = :stock_id`)
  3. `Current_Prices` row (`SELECT ... FOR UPDATE WHERE stock_id = :stock_id`)
- Consistent acquisition order mathematically eliminates AB-BA deadlock cycles.

---

## 9. AI Query Safety & RBAC Scoping
- The AI assistant pipeline operates on a decoupled architecture:
  1. **RAG Knowledge Retrieval**: Allowed views and rules per role.
  2. **LLM SQL Generation**: Returns structured JSON `{sql, tables, explanation}`.
  3. **SQLGlot AST Validation**: Whitelist-based validation of AST (only `SELECT`, authorized views and safe functions, no write or DDL keywords, limit clause enforcement).
  4. **Row-level Scope Enforcement**: Row tenancy is injected at runtime using MySQL session variables (`@current_user_id`) and scoped views (`user_id = @current_user_id` for investors, `broker_id = @current_user_id` for brokers).
  5. **Read-Only Least-Privilege Execution**: Executed via a dedicated MySQL user `stocktrade_ai_ro` with read-only view privileges and a strict query timeout (`5s`).
